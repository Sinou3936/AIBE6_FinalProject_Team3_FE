# 임장 체크리스트(checklist) 도메인 — Frontend 구현 현황 정리

## 배경 / 성격

`auth-design.md`/`user-design.md`/`property-design.md`/`market-data-design.md`와 같은 성격의 **요구사항 명세서 대비 실제 구현 대조 문서**입니다. Backend `docs/specs/checklist-design.md`가 이미 API 레벨에서 같은 대조를 해뒀으므로, 이 문서는 **그 API를 실제로 소비하는 화면**이 요구사항과 얼마나 일치하는지만 다룹니다. Backend 쪽에서 이미 지적된 이슈(템플릿 유형 무관 공통 적용, 삭제된 매물 재검증 누락, 정렬 로직 없음 등)는 FE도 그대로 이어받으므로 중복 설명 대신 해당 문서를 참조 표시합니다.

**범위**: `app/(main)/properties/[id]/checklist/**`, `app/(main)/checklists/**`, `app/services/checklist.ts`, `app/mappers/checklist.ts`, `app/data/checklist.ts`만 다룹니다.

## 주요 화면 / 파일

| 파일 | 역할 |
| --- | --- |
| `app/(main)/properties/[id]/checklist/page.tsx` + `ChecklistClient.tsx` | 체크리스트 생성/조회/항목확인/결과확인 화면 |
| `app/(main)/checklists/page.tsx` + `ChecklistOverviewClient.tsx` | 매물별 체크리스트 현황 목록 (요구사항엔 없는 화면 — 아래 "추가 구현" 참고) |
| `app/services/checklist.ts` | `POST/GET /properties/{id}/checklists`, `PATCH /checklists/{id}/items/{itemId}`, `GET /checklists/{id}/result`, `GET /checklists` 호출 |
| `app/data/checklist.ts` | 5개 카테고리 탭 정의(아이콘/이름/순서) |

## 체크리스트 생성 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 매물 상세 화면에서 시작 | ✅ `PropertyDetailClient`의 "현장 체크리스트 시작" 버튼(오늘부터는 `/checklists` 목록 화면에서도 진입 가능) |
| 매물 접근 권한 확인 | Backend 책임(오늘 FK 전환하면서 존재/소유권 검증 추가함 — `checklist-overview-list-design.md` 참고) |
| 매물유형·거래유형 맞는 템플릿 생성, 20~24개·5개 카테고리 | ⚠️ **(2026-07-29 갱신)** Backend가 템플릿 v2로 올리면서 매물유형별 문항 필터링(`applicablePropertyTypes`)을 일부 도입함 — 잠금장치 문항이 "공동현관과 현관문"(오피스텔·연립다세대) / "현관문만"(단독·다가구) 둘 중 하나만 노출되도록 얇게 분기됨. 다만 이건 템플릿 전체를 유형별로 나눈 게 아니라 문항 하나만 조건부로 필터링한 것이라, "유형 무관 공통 템플릿"이라는 Backend 문서의 지적이 완전히 해소된 건 아님. 거래유형(전세/월세) 기준 분기는 여전히 없음. FE는 이 필터링에 관여하지 않음 — Backend가 이미 걸러서 준 항목만 그대로 5개 탭에 나눠 표시할 뿐이라 별도 대응 불필요 |
| 서류·행정 세부 항목에 안내 문구 제공 | ✅ 각 항목의 `guideText`를 카드에 그대로 노출(`{item.guideText && <p>...}`) — "왜 확인해야 하는지"를 짧게 설명하는 사용성 요구사항과 정확히 맞음 |
| "최근 소유권 변경 + 높은 전세가율" 보조 신호(risk-analysis 연계) | ❌ **미구현.** 화면 어디에도 이런 조합 신호를 표시하는 코드가 없음. risk-analysis 도메인 자체가 아직 연동 전이라 Property 상세 화면의 "확인 필요 신호" 섹션도 항상 "준비 중" 상태(`property-design.md` 참고) — 이 항목도 그 상태에 종속됨 |
| 기존 체크리스트 있으면 재생성 안 함 | ✅ `createOrGetChecklist`가 GET 먼저 시도하고 404일 때만 POST(멱등) |
| 실패: 존재하지 않는 매물/접근권한없음/매물정보부족/미지원유형 | ⚠️ 4가지 사유 구분 없이 "체크리스트를 불러오지 못했습니다. API 설정을 확인해 주세요." 단일 문구(다른 도메인과 동일한 pass-through 패턴) |

## 체크리스트 조회 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 접근 권한 확인 | Backend 책임 |
| 카테고리·중요도 순 정렬 | ✅ **(2026-07-29 해결)** Backend가 `ChecklistResponse.from()`에서 카테고리→중요도→`displayOrder` 순으로 정렬해서 응답을 내려주도록 바뀜(카테고리 순서는 FE `app/data/checklist.ts`와 동일하게 맞춤 — 서류·행정이 마지막). FE는 `items.filter(item => item.category === activeCategory)`로 카테고리만 걸러낼 뿐 배열 순서는 그대로 보존하는 구조라, 서버 정렬이 자동으로 반영됨(코드 변경 불필요). PATCH 이후 로컬 갱신(`applyUpdate`)도 `.map()`으로 인덱스를 유지해 순서가 흐트러지지 않음 |
| 확인/주의 항목 구분 | ✅ `issueFound === true`인 카드에 주황 테두리(`border-orange-200 bg-orange-50/40`) |
| 실패: 존재하지 않는 체크리스트/접근권한없음/삭제된 매물 연결 | ⚠️ **(2026-07-29 갱신)** `GET /properties/{propertyId}/checklists`가 이제 404(체크리스트 없음)와 403(매물은 있지만 본인 소유 아님)을 구분해서 반환함. FE `createOrGetChecklist`(`services/checklist.ts`)는 이미 `error.status === 404`일 때만 POST로 재시도하고 그 외(403 포함)는 그대로 throw하는 구조라 **동작 자체는 변경 없이 이미 올바름** — 예전엔 GET이 항상 404만 줘서 불필요하게 POST까지 시도했다가 그 안에서 403을 받았는데, 이제는 GET 단계에서 바로 403을 받아 헛된 POST 호출 하나가 줄어드는 정도의 차이. 다만 화면엔 여전히 403도 다른 실패와 똑같이 "체크리스트를 불러오지 못했습니다. API 설정을 확인해 주세요."로 뜬다 — 이제는 확실히 구분 가능한 상태지만, 정상적인 화면 흐름으로는 이 403을 만날 방법이 없어서(목록→클릭, 매물 상세→체크리스트 어느 경로로도 남의 매물 id에 접근하지 않음, URL 직접 조작해야만 발생) 문구를 구체화할 실익이 적다고 판단해 우선순위를 낮게 둠(브레인스토밍 결론). **삭제된 매물 재검증은 이제 조회 시점에도 적용됨(2026-07-29, 아래 비기능요구사항 표 참고)** |

## 체크리스트 항목 확인 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| CHECK 항목: 등기부등본 세부(신탁등기/명의일치/소유권취득일)는 Y/N 또는 날짜로 직접 입력 | ✅ `itemType`이 `YES_NO`/`DATE`인 항목은 각각 예/아니오 버튼, 날짜 입력으로 렌더링 |
| 서류 요청 결과(제공됨/미제공) 반영 | ✅ `DOCUMENT_REQUEST` 타입 항목은 "제공받음"/"미제공" 버튼 |
| 서류 미제공/신탁등기 있음/명의불일치 시 자동 `issueFound` | Backend 계산 결과를 FE가 그대로 표시만 함. 다만 "명의 일치" 항목은 Backend 문서가 이미 "질문 방향이 요구사항과 반대(일치 여부를 물어서 N이 불일치)"라고 짚어뒀고, FE는 백엔드가 내려준 `content`/`guideText`를 그대로 렌더링하므로 이 방향 차이를 그대로 이어받음 |
| 상태 변경 결과를 즉시 화면에 반영 | ✅ **optimistic update** — API 응답을 기다리지 않고 클릭 즉시 로컬 상태를 먼저 바꾸고(`setItems`), 실패하면 해당 항목만 롤백(`applyUpdate`의 catch에서 항목 단위로 되돌림) |
| 실패: 존재하지 않는 항목/권한없음/잘못된 상태값/삭제된 매물 | ⚠️ 단일 문구("저장하지 못했어요. 다시 시도해 주세요.") + 해당 항목 롤백. 사유 구분 없음(**2026-07-29**: Backend가 삭제된 매물이면 항목 수정 시점에도 404로 막도록 고쳤지만, FE는 여전히 모든 실패를 동일 문구로 표시). 세션 만료 관련은 **2026-07-29** `requestJson()`에 브라우저 전용 자동 refresh-then-retry가 들어가 대부분 조용히 복구되고, 그래도 실패하면(주로 `unreachable`) 아래 5번 항목의 `isSessionInvalidErrorCode` fallback이 처리 — 더 이상 "자동 재발급 대상이 아님"은 아님(`auth-design.md` 이슈 2번 참고) |

## 체크리스트 결과 확인 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 필수 확인 누락 수 / 주의 항목 수를 개수로 표시 | ✅ `summary.missingRequiredCount`/`summary.cautionCount` — 등급·점수 없이 개수만 |
| 시작 전이면 "체크리스트를 시작해보세요"로 대체 | ✅ `summary.hasStarted ? ... : (summary.message ?? '체크리스트를 시작해보세요')` |
| 실패: 존재하지 않는 체크리스트/확인한 항목 없음/결과 계산 실패 | Backend `checklist-design.md`가 이미 "확인한 항목 없음"은 실제로 실패가 아니라 성공(NOT_STARTED 안내)으로 처리된다고 지적함 — FE는 이 성공 응답을 그대로 받아 "시작해보세요" 문구로 보여주므로, 요구사항의 "실패 사유" 목록과는 자연히 안 맞고 Backend의 "시스템 처리" 설명과는 일치함 |

| 항목 | 요구사항 | 실제 |
| --- | --- | --- |
| 매물·거래유형 맞는 항목 생성 | O | Backend 책임 — **(2026-07-29 갱신)** 매물유형은 일부 지원(잠금장치 문항 필터링), 거래유형 기준 분기는 여전히 미지원(위 "체크리스트 생성" 표 참고) |
| 동일 조건 동일 버전 템플릿 | O | Backend 책임 |
| 템플릿 변경 이력 버전 관리 | O | Backend 책임(Backend 문서가 "정수 상수 하나뿐, 실제 이력 관리 없음"이라고 지적) |
| 유저-매물 조합당 활성 체크리스트 1개 | O | Backend 책임(DB 유니크 제약) |

| **삭제된 매물의 체크리스트는 수정 불가** | O | ✅ **(2026-07-29 해결)** Backend가 조회(`GET`)·항목수정(`PATCH`) 시점 모두에서 매물 삭제 여부를 재검사하도록 수정 — 삭제된 매물이면 404를 반환함. FE는 이 검증에 관여하지 않고 Backend 응답을 그대로 신뢰하는 구조라 별도 코드 변경 없이 자동으로 안전해짐 |
| 항목은 짧고 명확하게 | O | Backend 시드 데이터 문구 그대로 렌더링(FE가 가공하지 않음) |
| **필수/일반 항목 구분 표시** | O | ⚠️ **개별 항목 카드에는 구분 표시가 전혀 없음.** `importance` 필드는 응답에 있지만 화면의 항목 카드 어디에도 "필수"/"일반" 배지가 없다 — 유일하게 노출되는 곳은 상단 요약 카드의 "필수 확인 누락 N개"라는 **집계 숫자**뿐이라, 지금 체크 중인 항목 하나하나가 필수인지 일반인지는 사용자가 알 수 없음 |
| "안전 점수" 대신 확인완료도/주의항목수 | O | ✅ |
| 체크 상태 변경 즉시 반영 | O | ✅ optimistic update |
| 등기부등본 세부 항목에 안내 문구 | O | ✅ `guideText` 렌더링 |
| 반복 요청에도 중복 저장 안 됨 | O | Backend 책임(덮어쓰기 구조) |
| 저장 실패한 항목을 완료로 표시 안 함 | O | ✅ 실패 시 해당 항목만 이전 상태로 롤백 |
| 항목 하나 변경 시 전체 재생성 안 함 | O | ✅ `PATCH` 하나만 호출, 목록 전체를 다시 저장하지 않음 |
| 조회 시 매물 불필요 상세정보 미조회 | O | ✅ 체크리스트 조회는 체크리스트 필드만 요청 — 매물 상세는 오늘 추가한 헤더 표시용으로 별도 호출(`getPropertyById`)이며, 실패해도 체크리스트 조회 자체엔 영향 없음(`checklist-overview-list-design.md` 참고) |

## 요구사항에 없던 추가 구현

- **`GET /checklists`("내 체크리스트 목록") 및 `/checklists` 화면** — Backend 문서에도 동일하게 명시됨: 요구사항 명세서엔 없는 엔드포인트/화면. 매물마다 진입점이 따로 없어 상단 네비게이션 "현장 체크" 메뉴가 갈 곳이 없었던 문제를 해결하기 위해 오늘 추가함
- **CHECK 항목의 "완료/미흡 + 메모"** — 요구사항은 CHECK 항목을 단순 체크(확인/미확인)로만 전제하는데, 실제 구현은 "완료"/"미흡" 2버튼 + 미흡 시 텍스트 메모(`userNote`)까지 지원. `hasIssue = issueFound(서버 자동 판단) || userNote != null(사용자 주관적 표시)`로 병합해서 "주의 항목" 카운트 하나로 통일해 보여줌
- **체크리스트 완료 시 "특약사항 분석하기" CTA 버튼** — 필수 항목을 모두 채우면(`missingRequiredCount === 0 && hasStarted`) 계약서 분석 화면으로 넘어가는 버튼이 뜸. 요구사항엔 도메인 간 이동 흐름 언급이 없음
- **체크리스트 상세 헤더의 매물 정보 표시**(오늘 추가) — 요구사항엔 없지만, 목록 화면에서 여러 매물의 체크리스트를 오갈 수 있게 되면서 "지금 보고 있는 게 어느 매물인지" 표시가 필요해져 추가함
