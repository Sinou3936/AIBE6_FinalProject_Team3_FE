# 계약 문구 분석(contract-analysis) 도메인 — Frontend 구현 현황 정리

## 배경 / 성격

다른 도메인 문서와 같은 성격의 **요구사항 명세서 대비 실제 구현 대조 문서**입니다. 다만 이 도메인은 **Backend가 아직 작업 진행 중**(`CLAUDE.md` 기준 4단계 파이프라인 중 담당자가 계속 구현 중)이라, 여기 적힌 내용은 오늘 시점의 스냅샷일 뿐 곧 달라질 가능성이 높습니다. 다른 도메인 문서보다 "미구현"이 압도적으로 많은데, 이는 Frontend가 잘못 만들었다기보다 **아직 이 화면 자체가 정적 목업(static mockup) 단계**이기 때문입니다.

**범위**: `app/(main)/contract/upload`, `app/(main)/contract/result`, `app/services/contract-analysis.ts`, `app/mappers/contract-analysis.ts`만 다룹니다.

## 핵심 요약: 입력 → 분석 파이프라인이 실제로 연결되어 있지 않음

가장 먼저 짚어야 할 사실: **사용자가 업로드 화면에서 무엇을 입력하든, 결과 화면은 항상 똑같은 하드코딩된 문장을 분석한 결과를 보여줍니다.**

- `app/(main)/contract/upload/page.tsx`의 "직접 입력" `<textarea>`는 `value`/`onChange`가 없는 **완전히 비제어(uncontrolled) 컴포넌트**라, 사용자가 타이핑해도 그 값을 저장하는 state 자체가 없음
- 이미지 드래그앤드롭 영역의 `onDrop` 핸들러는 `preventDefault()`만 하고 파일을 실제로 읽거나 저장하지 않음. "직접 촬영"/"PDF 일부" 버튼도 `<input type="file">` 연결이 전혀 없는 장식용 버튼
- "특약사항 분석하기" 버튼은 API를 호출하는 게 아니라 그냥 `<Link href="/contract/result">`일 뿐이고, 활성화 조건도 사용자가 입력한 내용과 무관하게 **자가 체크 3개 체크박스**("특약사항만 올렸어요", "개인정보 가렸어요", "동의합니다")만 확인
- `app/(main)/contract/result/page.tsx`는 사용자가 무엇을 입력했는지 전혀 알지 못한 채, 파일 안에 하드코딩된 `demoSpecialTermsText`("임대인은 개인 사정에 따라... 명도를 요청할 수 있다...")를 항상 `analyzeContractSpecialTerms()`에 보내 분석합니다

즉, `analyzeContractSpecialTerms()` 서비스 함수와 `POST /contracts/special-terms/analyze` 호출 자체는 실제로 동작하지만(mock 모드가 아니면 진짜 API를 호출함), **그 입력값이 사용자 입력과 완전히 무관한 고정 문자열**이라 기능적으로는 데모 그 이상이 아닙니다.

## 개인정보 마스킹 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 전화번호/주민등록번호/계좌번호 등을 시스템이 정규식·라벨 기반으로 마스킹 | ❌ **미구현.** 시스템이 마스킹을 수행하는 로직이 없음 |

| 마스킹 결과는 서버 저장 없이 프론트에서만 확인 시점까지 보관 | N/A — 마스킹 자체가 없으니 보관할 대상도 없음 |
| 마스킹 확인 안 하면 AI 분석 요청 안 함 | ⚠️ 체크박스 3개를 다 눌러야 다음 화면으로 가는 건 맞지만(`allChecked`), 그 다음 화면에서 실제로 전송되는 건 사용자가 확인한 내용이 아니라 하드코딩된 데모 문장(위 "핵심 요약" 참고) |

## AI 계약 문구 분석 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 확인된 마스킹 텍스트만 AI로 전송 | ❌ 위 "핵심 요약" 참고 — 사용자 입력이 아니라 항상 고정 문자열이 전송됨 |
| 위험 여부/이유/쉬운 설명/확인 질문/수정 예시 제공 | ✅(응답 형태 자체는) — `ContractRiskItem`이 `original`/`simple`/`why`/`question`/`suggestion`을 전부 담고 화면에도 다 표시됨. 다만 위 이유로 항상 같은 입력에 대한 같은 결과 |
| "AI가 생성한 결과입니다" 고지 상시 포함 | ⚠️ 매 조항(clause)마다가 아니라 **페이지 하단에 한 번만** 고지 문구가 있음("본 분석 결과는 참고 정보이며 법률 자문이나 계약 안전을 보장하지 않습니다") |
| 법적 효력 없는 참고 정보 안내 | ✅ 위와 동일한 문구로 포함 |
| 수정 요청 문구에 "법률적 정답 아닌 협의용 예시" 안내 | ⚠️ 개별 수정 예시 옆이 아니라 페이지 공통 하단 문구 하나로 퉁쳐짐 — 요구사항은 "수정 요청 문구에는" 이라고 해당 문구 단위로 명시했는데 실제는 페이지 단위 |
| AI 응답 구조/입력에 없는 내용 포함 여부 서버 검증 | Backend 책임, FE 범위 밖(진행 중) |
| 실패 사유 6종 제공 | ⚠️ `loadError` 하나로 뭉뚱그림("계약 분석 결과를 불러오지 못했습니다. API 설정을 확인해 주세요.") |

## 요구사항에 없던 추가 구현

- "보증금 안전성"/"누락 항목" 탭 — 요구사항 문서의 contract-analysis 섹션엔 없는 내용(risk-analysis 도메인에 가까운 내용). 지금은 완전 정적 데이터라 실제로 어느 도메인 API와 연결될지는 아직 불명확
- PDF 저장/결과 공유/질문 복사/문구 복사/전문가 상담 버튼 — 전부 장식용(onClick 없음), 요구사항에 없는 부가 기능으로 자리만 잡아둔 상태

## 남은 이슈 / 확인 필요 총정리

1. **입력(이미지/텍스트) → 분석 파이프라인이 완전히 끊어져 있음** — 사용자가 뭘 입력하든 항상 같은 데모 문장이 분석됨. 이 도메인에서 가장 시급하고 근본적인 이슈. Backend 4단계 API가 준비되는 시점에 맞춰 업로드 화면의 상태 관리(텍스트/이미지 캡처, 페이지 간 데이터 전달)부터 새로 설계해야 함
2. **OCR/마스킹 단계 자체가 FE에 없음** — 특히 마스킹은 "시스템이 자동으로 가리고 사용자가 확인"이 아니라 "사용자가 본인이 가렸다고 자가 신고"하는 완전히 다른 UX로 대체돼 있어, Backend가 실제 마스킹 기능을 붙일 때 이 화면을 통째로 다시 설계해야 함
3. **`/contract/result`의 `<Link href="/properties/1/checklist">` 하드코딩이 아직 안 고쳐짐** — 이전에 "내 체크리스트 목록" 작업 때 스코프 밖으로 미뤄뒀던 것(`checklist-overview-list-design.md` 참고)이 그대로 남아있음. 지금은 `/checklists`로 보내는 게 자연스러움
4. **"AI 생성 결과", "협의용 예시" 고지가 조항/문구 단위가 아니라 페이지 전체에 한 번만** — 요구사항 문구를 엄격히 따지면 각 결과 단위로 필요해 보이는데 지금은 뭉쳐서 하단에 한 번
5. **"보증금 안전성" 탭이 완전 정적 목데이터** — 이 탭이 결국 risk-analysis/market-data 도메인 데이터로 채워져야 하는지, contract-analysis 자체 범위인지 확인 필요
